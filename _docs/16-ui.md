# 16 — The Fallout UI

Phoenix's `fallout_ui` library ported onto Helix. Lives in
`gamemodes/falloutrp/schema/fallout_ui/`, three files, loaded in this order
from `sh_schema.lua` — **the order matters**, the other two read the theme at
load time.

| File | Contains |
|---|---|
| `cl_theme.lua` | palettes, fonts, `sW`/`sH`, `surface.DrawEdgedBox`, `surface.RoundedOutlineBox`, fades, options |
| `cl_widgets.lua` | `ix.fallout.DrawBrackets`, UI sounds, the `ixFO*` widget set |
| `cl_skin.lua` | overrides Helix's derma skin + the accent-colour bridge |
| `cl_panels.lua` | patches Helix's own registered panels, `fo_ui_report` |
| `cl_hud.lua` | New Vegas HUD, Fallout 4 HUD, compass, radiation counter |

## How Helix gets restyled — two levers, not one

This is the thing to understand before changing anything here. Helix panels
take their appearance from **two separate places**, and covering only one
leaves half the UI stock.

**1. The derma skin.** Helix registers one skin, `"helix"`, via
`derma.DefineSkin`. `cl_skin.lua` reaches into `derma.SkinList["helix"]` after
Helix has loaded and replaces its paint functions in place. This covers
everything that paints through derma's skin dispatch — stock `DFrame`,
`DButton`, `DMenu`, `DComboBox`, scrollbars, and the places Helix calls a
`SKIN:` function explicitly.

**2. `ix.config.Get("color")`.** Most of Helix's *own* panels — notices, the F1
menu and its buttons, inventory, scoreboard, character load, settings rows,
tooltips — define their own `Paint` and never touch the skin. They read their
accent from `ix.config.Get("color")`, **35 call sites** across the gamemode.
`cl_skin.lua` wraps that getter clientside so it returns the player's palette
colour.

Between the two, the whole interface follows the Pip-Boy colour. **Helix itself
is never edited** — updating it won't clobber any of this.

The wrapper is client-only and keyed on `"color"` alone, so the server's stored
config value, its replication, and the admin config menu are untouched. It is
guarded by `ix.fallout.configPatched` so an autorefresh doesn't stack wrappers.

## Palettes

Five, chosen per client via the `falloutTheme` option. `orange` (default),
`green` and `pink` are Phoenix's exact values; `blue` and `white` are additions.

`ix.fallout.GetPalette()` returns the resolved table. It's **cached** — rebuilt
only when the option changes, never per frame. Derived shades live on it too:

| Field | Use |
|---|---|
| `color_primary` | the accent |
| `color_bright` | primary + 24, what Phoenix's `drawBar` computed inline every frame |
| `color_dark` | primary × 0.8, HUD ticks |
| `color_faint` | primary × 0.2, bar backgrounds |
| `color_background`, `color_active`, `color_outline`, `color_selected` | panel work |

Changing the palette fires `FalloutPaletteChanged`, and that re-fires Helix's
own `ColorSchemeChanged` for anything that caches the accent.

## Fonts

Phoenix's ten `UI_*` fonts, at their 1080p sizes, **scaled by screen height**
(`math.Clamp(ScrH() / 1080, 0.75, 2)`). Phoenix's are fixed pixel sizes, so
their HUD shrinks to nothing at 1440p and above.

Each font gets a `_Blur` twin, same convention Helix uses.

`ix.fallout.LoadFonts()` runs at load, again on `InitPostEntity`, and again on
`OnScreenSizeChanged`. The re-run matters for more than resolution changes:
**`longsword_base` also defines `UI_Regular` and `UI_Bold`** as a standalone
fallback, and re-running guarantees the schema's versions win regardless of
which loaded first.

`weight = 10000` in Phoenix's originals is written as `1000` here — the engine
caps weight at 1000, so those were always identical.

### A panel in `derma/` cannot touch `ix.fallout` at file scope

Helix's own load order, from `core/libs/sh_plugin.lua`:

```
ix.util.IncludeDir(path.."/libs", true)      -- line 43
ix.util.IncludeDir(path.."/derma", true)     -- line 49
ix.util.Include(path.."/sh_schema.lua")      -- line 55
```

`sh_schema.lua` is what includes `fallout_ui/cl_theme.lua`, so **while a
`derma/` file is being read, `ix.fallout` does not exist yet**. Anything in one
of those files that runs at file scope and reaches for the theme — a scale, a
palette colour, a font built from `GetFontScale()` — throws.

The failure is unusually quiet. The error aborts the file *before* the
`vgui.Register` at the bottom, so the panel class is never registered,
`vgui.Create` returns nil, and the command that opens it does nothing at all.
There is no error at the point you press the button; the only trace is a load
error that scrolled past minutes earlier.

This is what `cl_lootconfig.lua` hit: it built its own fonts with a
`LoadFonts()` call at file scope, and `/lootconfig` silently opened nothing.
Fonts are now created from `PANEL:Init` — late enough, and the only moment they
are needed — with a guard on `ix.fallout` covering the
`OnScreenSizeChanged` hook firing in the same window.

Function *bodies* are fine, since they only run once something calls them.
Anything else — a `Color(...)`, a table of strings — is fine too. The rule is
narrow: **no theme reads at file scope in `derma/`**.

(A `vgui.Register` whose base class lives in `fallout_ui/` is fine despite
loading first: derma resolves the base name at `vgui.Create` time, not at
registration.)

## The HUD

Two styles plus a compass, selected with the `falloutHud` option
(`nv` / `f4` / `none`).

**New Vegas** — the bracketed left/right plates (`phoenix/hud/leftbar.png`,
`rightbar.png`) with 43 tick marks each for HP and AP, ammo bottom-right,
condition icons stacked at the left.

**Fallout 4** — flat labelled bars.

Both suppress Helix's own HUD through hooks that exist under the same names
NutScript used: `ShouldHideBars` and `CanDrawAmmoHUD`.

### Providers — the important bit

Phoenix's HUD calls `char:getHunger()`, `getThirst()`, `getRadiation()` and
`nut.races:hasHunger()` directly. **None of those exist in our schema**, and a
direct call would be a nil-index error every frame.

Everything goes through `ix.fallout.hud.providers` instead. A provider returns
`value, max`, or **nil when that system isn't installed** — and the HUD then
omits that readout entirely rather than drawing an empty bar.

```lua
ix.fallout.hud.providers.hunger = function(client)
    local character = client:GetCharacter()
    if (not character) then return end
    return character:GetData("hunger", 100), 100
end
```

That's the whole change needed when hunger lands. `health` and `stamina` are
already wired — Helix's stamina plugin uses the same `stm` local var NutScript
did, so the AP meter works as-is when that plugin is on.

### Radiation counter

`ix.fallout.hud.ShowRadiationGain(rads)` drives the spinning counter, so a
future radiation system triggers it without touching the HUD. A
`net.Receive("ixRadiation:Update")` is already wired to it.

Its tick sounds live in a Phoenix sound pack **we don't have installed**, so
playback is behind a one-time `file.Exists` check — `PlaySound` on a missing
file spams the console.

## Overriding a skin function — read the original first

The single most important rule in this file, learned the hard way.

Helix's skin functions are **not purely cosmetic**. Several do functional work
that the calling panel relies on and does not do itself:

| Function | Functional work it does |
|---|---|
| `PaintChatboxEntry` | `panel:DrawTextEntryText(...)` — draws the text, selection and caret. `ixChatboxEntry` overrides `DTextEntry:Paint` entirely, so nothing else draws them |
| `PaintCategoryPanel` | returns four numbers used as docking padding |
| `PaintInfoBarBackground` | calls `PaintManual()` on the bar and label children |
| `PaintChatboxBackground` | branches on `panel:GetActive()` |
| `PaintChatboxAutocompleteEntry` | animates through `panel.highlightAlpha` |
| `PaintChatboxTabButton` | reads `panel:GetUnread()` / `panel.unreadAlpha` |

Dropping any of these throws **no error**. The feature just silently stops
existing — which is how a dropped `DrawTextEntryText` presented as "the chatbox
won't let me type" when input was working perfectly the whole time.

Before replacing `SKIN:PaintX`, grep Helix's `cl_skin.lua` for that function and
look for `panel:` calls and `return`.

## Inverted highlights and text colour

Fallout inverts selection — solid fill, dark text. Derma does not cooperate:
button, menu and title text colours come from `SKIN.Colours.*`, which this skin
sets to the palette colour. **Filling a background solid with that same colour
renders invisible text.**

So: highlights are translucent (`ColorAlpha(primary, 45–90)`) and the outline
carries the state. True inversion is used in exactly two places, both of which
control their own text — the category header (draws its text black directly) and
the frame title strip (`SKIN.Colours.Window.TitleActive = color_black`).

## NV HUD meter geometry

Phoenix positions each tick from its own fraction of the plate width — 43 ticks
at 0.0175 wide, 0.003 apart. The run length is whatever those happen to sum to,
which is not tied to the artwork and shifts as rounding changes with resolution.

Here the **slot is the primitive**:

```lua
local slotW = w * cvarSlotW:GetFloat()
local step  = slotW / ticks
```

The last tick's right edge lands on `slotW` by construction, so the run cannot
overflow at any resolution. If the meters sit wrong against the plate art, move
the slot — see the `fo_hud_*` convars in `12-commands-and-workflow.md`.


## The bracket motif

`ix.fallout.DrawBrackets(w, h, color, inset)` is the single most recognisable
piece of the Fallout interface: a rule along the top and bottom with short ticks
turning down at each corner, drawn a couple of pixels **outside** the panel
(hence `DisableClipping`), with a one-pixel black shadow behind it.

Phoenix repeats those twelve `DrawRect` calls verbatim in four separate panels;
here it is one function, and the thickness scales with the font scale so it does
not vanish at 4K.

`inset` pulls the rules inward for panels that cannot overdraw their parent — a
scissor rect, most often.

## Widgets — `ixFO*`

Ported from Phoenix's `vgui/cl_fo_*.lua`.

| Class | Base | Notes |
|---|---|---|
| `ixFOPanel` | DPanel | plain palette fill |
| `ixFOPanelBracketed` | DPanel | the workhorse; `SetNoBackground` for brackets only |
| `ixFOFrame` | DFrame | title sits in a gap in the top rule |
| `ixFOButton` | DButton | inverts on hover |
| `ixFOLabel` | DLabel | |
| `ixFOTextEntry` | DTextEntry | solid field, dark text |
| `ixFOScrollPanel` | DScrollPanel | flat palette bar |

**These invert on hover and that is safe here**, unlike in the derma skin,
because each widget sets its own text colour in `Init` rather than inheriting it
from `SKIN.Colours`. That is the whole difference — see the section above on
inverted highlights.

Widgets cache colours in `Init`, so a `FalloutPaletteChanged` handler walks the
live panel tree and recolours anything already on screen.

UI sounds go through `ix.fallout.PlayUISound`, which checks the file exists once
and caches the result — Phoenix's sound pack is not installed and `PlaySound` on
a missing file logs once per click.

## Patching Helix's own panels — `cl_panels.lua`

The skin only reaches panels that paint through derma's skin dispatch. Helix's
own panels (inventory, notices, menu buttons) define their own `Paint`.
`vgui.GetControlTable(class)` returns the registered table, and patching it
restyles every instance without reimplementing the panel.

**Default to `Wrap`, not `Replace`.** Helix's panel methods routinely do
functional work alongside drawing:

| Method | Functional work |
|---|---|
| `ixNotice:Paint` | sets a scissor rect for the dismiss animation, runs its own hover detection |
| `ixItemIcon:Paint` | dispatches to `ExtraPaint` |

`Wrap` calls the original first and draws on top, so that work survives by
construction. `Replace` is used only where the original is verifiably nothing
but drawing, and each use says so in a comment.

### What is patched

| Panel | Change |
|---|---|
| `ixMenuButton` | UI_Bold, palette text, wash + solid leading edge on hover (drives off Helix's own `currentBackgroundAlpha`, so the animation is kept) |
| `ixItemIcon` | Fallout slot, equipped tint and corner flag, **item name printed on the icon** |
| `ixInventory` | icon size scaled by resolution instead of a hardcoded 64 |
| `ixNotice` | palette accent bar down the left edge |
| `ixCharMenuCarousel` | brackets |

### fo_ui_report

Patching fails **silently at the feature level** — a wrong class name means the
panel renders stock with no error. `fo_ui_report` prints every patch that
applied, any class that was not found, whether each widget registered, and the
active palette, HUD and scale. Run it after touching this file.


## F1 menu - `ixFOMenu`

The menu is a **replacement** for Helix's `ixMenu`, not a restyle. Phoenix did
the same: `nutMenu_fallout` is its own panel. The two layouts are not variations
of each other -

| | |
|---|---|
| Helix | a 25%-wide button column docked LEFT, content filling the rest |
| Phoenix | a centred 896x704 window, tabs in a horizontal strip inside it |

**A patch-based attempt failed and is worth not repeating.** Bending Helix's
docking into Phoenix's shape got the tabs horizontal and nothing else right:
button widths came from Helix's 32px text padding so the strip spanned the whole
screen, the right-docked "return"/"characters" buttons collided with the last
tab, and the subpanels kept their own geometry. Docking fights you when the
layout disagrees with it, so `ixFOMenu` positions everything **manually in
PerformLayout**.

Geometry follows Phoenix's `derma/cl_menu.lua` exactly: a 896x704 window centred
with a +16 vertical nudge, a 36px tab strip along the top with the buttons
centred as a group, an info bar along the bottom, page area between them.

**Tab content is still Helix's.** Tabs come from the same `CreateMenuButtons`
hook and are populated with Helix's own dispatch:

```lua
if (istable(info) and info.Create) then info:Create(container)
elseif (isfunction(info)) then info(container) end
```

so every tab any plugin registers keeps working, unmodified. Pages are built
lazily and cached, as Helix does.

### The compatibility surface

Helix reads a specific API off `ix.gui.menu` from a dozen places, and any
replacement has to provide it: `:Remove()`, `:IsVisible()`, `.bClosing`,
`.currentAlpha`, `:GetActiveTab()`, `:SetCharacterOverview()`. That list is in
the file header.

### Falling back

```
fo_menu_layout helix      Helix's own menu
fo_menu_layout fallout    ixFOMenu (default)
```

`Schema:ScoreboardShow` creates the menu inside a `pcall` and reverts to Helix's
on error. A whole panel that cannot be tested from here needs a way back.

## Matching Phoenix's look

The most useful thing learned here: **Phoenix's menu paints almost nothing.**

```lua
menu:SetPaintBackground(false)                    -- container: nothing
page.Paint  = Color(0, 0, 0, 100), inset by 6     -- translucent black
-- the tab rule BREAKS around the active tab:
surface.DrawRect(0, 30, bX + 6 + b, 2)            -- segment left of it
surface.DrawRect(s, 30, menu:GetWide() - s, 2)    -- segment right of it
```

No phosphor wash. No scanlines. No opaque fills. The neutral dark look is plain
translucent black over the blurred world, plus amber rules and bracket corners -
and that neutrality is exactly what makes the amber text read as a screen.

**Three attempts here went the wrong way by adding effects**: an opaque window
fill, a phosphor bloom, and heavy scanlines, all in pursuit of "more Pip-Boy".
The bloom is what turned the whole window olive. Restraint is the effect.

Specific consequences, all now following the source:

| Element | Phoenix | Why it matters |
|---|---|---|
| Window container | paints nothing but its outline | any fill tints everything inside it |
| Page | `Color(0, 0, 0, 100)` inset 6 | neutral, world faintly visible through it |
| Active tab | the rule **breaks** around it | a filled highlight box is not their look |
| Tab buttons | plain DButton, no background | an `ixFOButton` would flip its text dark on hover, invisible with no fill behind it |
| Info bar | each readout in its own bordered box | reads as instrument panels, not a text row |

### Scanlines

Kept, but only on the page and at alpha 16 - enough to suggest a screen without
tinting. Off via the `falloutScanlines` option.

## Side panels

`ix.fallout.menuMetaRows` drives the Meta Info panel to the right of the window,
the same data-driven shape as the HUD providers and the info-bar cells. Rows
carrying data today: character name, SteamID, faction, class, run/walk speed,
jump power. Phoenix also shows karma, fear and resistances - one entry each once
those systems exist.

Its height is measured during paint and consumed by `PerformLayout`, so it calls
`InvalidateLayout` when the measurement changes; without that it would sit at
its fallback height forever.

## Clipped corners belong on leaves, not containers

`cl_skin.lua` has two corner constants:

```lua
local EDGE = 8            -- leaf widgets: buttons, combo boxes, entries
local CONTAINER_EDGE = 0  -- anything with docked children
```

A clipped corner cuts diagonally across a panel's edge. Anything docked inside
is square and full-width, so the child's corner sticks out **through** the cut.
On category panels, settings rows and config sections that reads exactly like
the content is spilling outside its own frame - which is what it looked like.

Phoenix does not clip container corners either; they bracket them.

This cost two rounds of misdiagnosis. The symptom ("stuff going outside the
lines") looks like a sizing problem, and the first fix attempt widened the menu
window from 47% to 70% of the screen - which did not help, because nothing was
too narrow, and made the whole UI oversized instead.

## Menu inventory sizing

`FitParent` looks like the right tool and is not. It divides the parent by the
grid dimension, so the grid always consumes an entire axis - with a 10x7
inventory that means enormous slots filling the page edge to edge.

Phoenix's grid is 10 columns of roughly 64px inside an 896px window: it sits in
the middle with clear space around it. So the slot size is **fixed** (64 at
1080p, scaled), shrunk only if the grid would not otherwise fit, and the
container is padded horizontally to centre it.

Resizing goes through Helix's own `SetGridSize`, which accounts for both dock
paddings, sets the minimum size and rebuilds the slots. Doing that arithmetic by
hand drifts from it.

Two ordering traps in that code, both commented at the call site:

- the work is deferred one frame, because the container is not laid out when
  `MenuSubpanelCreated` fires
- `container:InvalidateLayout(true)` must run before `canvas:Layout()`, since
  the canvas takes its size from docking - set the padding without it and the
  canvas keeps its old width, so nothing moves

Geometry at 2560x1440: window 1196x939, page 1170x820, 85px slots, grid 858x595,
156px clear each side.

### The corner-to-middle jump

The inventory used to appear in the top-left of the page and move to the middle
every time the menu was opened, and it had done since the grid was first fitted.
It was never an animation: the deferred frame above is a frame in which Helix
**draws the panel** at its own default position and size, and what looked like a
slide was one frame of the truth followed by ours.

So the panel's alpha is set to zero the moment the subpanel is created, and back
to 255 at the end of the deferred pass, once it has been sized, rebuilt and
centred. Alpha rather than `SetVisible`, because a hidden panel is skipped by
layout and the measurements would then be taken against a panel that had not
arranged itself.

`Reveal` is called on **every** path out of that timer, including the ones that
give up early, and a half-second backstop timer calls it too: an inventory left
invisible because the character had not loaded yet would be a worse bug than the
one being fixed.


### Layout convars do not persist

`fo_menu_width`, `fo_menu_height` and `fo_menu_iconsize` are created with the
save flag **false**. A saved value beats a later change to the default, which is
how an experimental 0.70 kept the menu oversized after the default had been
corrected to Phoenix's 0.467. While these numbers are still being tuned the code
stays the single source of truth; flip the flag to true once they settle.


## Character menu

Helix's character menu is **already arranged the way Phoenix's is** — a button
column at the bottom left over a dimmed, blurred backdrop:

```lua
-- Helix, ixCharMenuMain:PerformLayout
self.mainButtonList:SetPos(padding, height - list:GetTall() - padding)

-- Phoenix, derma/cl_mainmenu.lua
menu:SetPos(ScrW() * 0.1, ScrH() - (ScrH() * 0.2 + sH() * 0.45))
menu:SetSize(212, sH() * 0.45)
```

So it is a restyle, not a rebuild — and the creation flow (faction, model,
description, attributes) keeps working untouched:

| Panel | Change |
|---|---|
| `ixCharMenu:Paint` | blur order fixed, and the map left **visible** - Phoenix only lightly darkens it |
| `ixCharMenuButtonList` | filled solid with `color_background` + brackets, narrowed from 25% of screen to ~13% (Phoenix's 212px at 1920) |
| creation / load backgrounds | light dim only; Phoenix's faction select and character list sit as panels over the live map |
| the buttons themselves | already `ixMenuButton`, covered by the panel patches above |

**No custom title.** Helix's own logo panel already draws the schema name and
description centre-screen, which is where Phoenix puts their logo. An earlier
pass drew a second one on top of it.

**`ixCharMenu:Paint` had the same inverted blur order** as the F1 menu — it dims
and then calls `DrawBlur`, which redraws the blurred world back over the dim.
That is now the third place this pattern has appeared in Helix.

### Docking beats SetPos

The single reason the main menu would not move. Helix does:

```lua
self.mainButtonList:Dock(LEFT)                              -- in Init
...
self.mainButtonList:SetPos(padding, height - tall - padding) -- in PerformLayout
```

A docked panel is repositioned by the layout engine every pass, so that `SetPos`
never took effect — **Helix's own positioning is dead code** — and neither did
anything set here. The panel stayed pinned full-height to the left edge no
matter what size or position was applied. `Dock(NODOCK)` first.

Same class of thing as the canvas: `SizeToContents` docks the scroll canvas to
BOTTOM whenever the list is taller than its content, stranding the buttons at
the foot of the panel. That is fixed in the layout pass rather than in
`SizeToContents`, which runs during Init before the panel has been resized.

### The panel sizes to its content

Phoenix's is `sH(486)` tall because it holds **seven** buttons — NEW, LOAD,
CONTENT, DISCORD, CHANGES, STEAM, STORE. Ours has four, so copying their height
literally left a large empty box below the last one.

The height is measured from the canvas children instead. The canvas is undocked
(so the buttons top-align rather than being stranded at the bottom), which also
means it does **not** auto-size — `canvas:GetTall()` is unreliable there, so the
children are measured directly.

Anchored by its **bottom** edge, which is Phoenix's rule rearranged:

```lua
y = ScrH() - (ScrH() * 0.2 + h)   -- bottom sits at 80% of screen height
```

so the panel grows upward as buttons are added and stays put otherwise.

Both size and position are written **only when they change**: `SetSize` inside a
layout pass schedules another one, and an unconditional write loops forever.

**The padding has to be applied before measuring.** The canvas is positioned
from the list's dock padding by the list's *own* `PerformLayout` — which has
already run this frame, with the padding still at zero, and setting it here does
not re-trigger it. Without a forced `InvalidateLayout(true)` the canvas sits at
y = 0 and every pixel of vertical padding piles up below the last button.

`fo_ui_report` showed this precisely: 4 buttons, content 244, padding 32 per
side, panel 308 — the arithmetic correct, but the content drawn from the top
edge. It now prints `canvas y` alongside, which should equal the padding.


### Width fits the widest button

Phoenix's column is a literal 212 wide because their buttons are single short
words — NEW, LOAD, CONTENT, STEAM. Ours read "LOAD CHARACTER" and "LEAVE
SERVER", which do not fit, so the label was ellipsized to "LOAD CHARACT...".

The width is measured from the widest button's text plus `ixMenuButton`'s own
`padding[1] + padding[3]`, with `sW(212)` as the floor — so it matches Phoenix
whenever the labels allow and grows only when they do not.

### Padding is a dock margin, not a canvas offset

`DScrollPanel:PerformLayout` ends with `pnlCanvas:SetPos(0, YPos)` — GMod's own
`dscrollpanel.lua`, lines 90 and 122 — and re-runs on every layout pass. **Any
canvas position set here is overwritten**, which is why two separate attempts at
offsetting it (first through dock padding, then directly) both left the content
flush to the top edge with all the padding piled below the last button.

The top padding is a `DockMargin` on the first button instead: the dock layout
applies margins itself and DScrollPanel never touches them. Because that margin
is inside the measured content, the panel height is `contentHeight + padY` —
bottom only — not `+ padY * 2`.

`fo_ui_report` prints **first button y**, which should equal the padding.
`canvas y` was the earlier check and was misleading: 0 is correct there.


### The screen going fully black

`ixCharMenuPanel` animates `currentDimAmount` up to `targetDimAmount`, which
Helix sets to **255** — fully opaque black — whenever it dims to hand off to
another subpanel. That is why character creation and the load screen rendered as
black rather than showing the map. Lowered to 120.

### Character creation text fields

`ixTextEntry:Paint` calls `DrawImportantBackground`, which is a **gradient**
helper — hence the smeared name and description boxes. Replaced with a solid
palette block and dark text, like Phoenix's terminal prompts.

`BaseClass.Paint` normally draws the text and cannot be reached from a patch, so
`DrawTextEntryText` is called directly. Same trap as the chatbox: omit it and
the field accepts input while displaying nothing.

### Every list, not just the main menu

The top-align fix lives on `ixCharMenuButtonList:PerformLayout`, not in the main
menu's layout, because the **load screen reuses the same class**. Doing it only
for the main menu left the character names pinned to the bottom of the load list.


### Panels must be opaque

`color_background` is a low-alpha colour by design — the amber palette's is
alpha 102. Drawing it alone, even raised to 235, lets the map through; against a
bright sky with a dark building behind it that reads as a *gradient* rather than
a flat panel. An opaque near-black base goes down first, then the palette tint.


## Character select

Helix's load screen already has Phoenix's shape:

```lua
controlList  Dock(LEFT), half the parent width, holds characterList
infoPanel    Dock(FILL), holds infoButtons (BOTTOM) and carousel (FILL)
```

Phoenix's differs in three ways, all additive — so this is a restyle, and their
loading, deletion and networking are untouched:

| Phoenix | Change |
|---|---|
| `self.characters:SetSize(256, ...)` | list column narrowed from half the screen |
| `self.info:SetTitle(name .. " >> " .. faction.name)` | header added above the model |
| `desc = self.info:Add("UI_DLabel")` | description under the header |

`controlList` and `infoPanel` are locals in Helix's `Init`, but both are
reachable through fields it does expose — `panel.characterList:GetParent()` and
`panel.carousel:GetParent()`.

The header paints from `panel.character` **every frame** rather than being
pushed on selection. Helix already keeps that field current in
`OnCharacterButtonSelected`, so reading it avoids a second copy of the selection
state that could drift.

### The model was loading but had no mesh

`fo_ui_report` showed the entity as `models/phoenix/humans/animations.mdl` while
nothing appeared on screen. That model is the animation **skeleton** and has no
visible mesh — the same reason players were invisible in-world, which
`libs/cl_bodyparts.lua` solves by bone-merging a body and head onto them.

**A part outlives its body unless something removes it.** A `ClientsideModel`
parented to an entity is unparented rather than removed when that entity goes,
and it then draws with no bone setup — a flat sliver of skin on the ground.
Every part is tagged `ixBodyPart` and `ix.fallout.SweepBodyParts` clears the
ones whose parent has gone, because the tracking tables cannot catch a leak by
definition: a leak is a part nothing holds a reference to.

The preview does the same, and shares the model paths: `ix.fallout.bodyParts`
and `ix.fallout.animationModel` are exposed from `cl_bodyparts.lua` so both
places change together once races replace the hardcoded human male set.

**The animation model stays the base entity**, with body and head merged onto
it. A first attempt made the *body* the base instead: that renders, but the body
model carries almost no animation data, so it stood in a T-pose. The animation
model is the one with the New Vegas set on it.

**`DModelPanel` draws only `self.Entity`**, so the merged parts need drawing
explicitly. That override goes on `DrawModel`, per instance — never on `Paint`,
which is the renderer. The base `DrawModel` is **captured and called**, not
replaced: `ixModelPanel:DrawModel` sets up all the model lighting first, and
replacing it leaves the preview flat and unlit.

`LayoutEntity` is wrapped the same way to face the model at the camera. Helix's
fixed `Angle(0, 45, 0)` suits the HL2 models its character creation was written
against and shows the *back* of these Fallout bodies. `fo_charpreview_yaw`
defaults to **0**, which points the model's forward axis at the camera — the
camera sits on the model's +X side, so the two have to be decided together.

### The sequence is `idle1`, not `idle`

Second T-pose, different cause. `animations.mdl` carries `idle1`..`idle4` plus
power-armour variants; there is no plain `"idle"`, so looking that name up
returned nothing and the entity sat on its reference pose. The lookup tries
`idle1`, `idle`, `idle_unarmed` in order and `fo_ui_report` prints whichever it
landed on.

### Framing has to measure the merged parts

The head kept getting cut off because the camera was framed from
`entity:GetRenderBounds()` — and the entity is the animation model, which has no
mesh, so those bounds are near-empty and put the camera almost inside the body.

Bounds come from the **merged parts** instead, combined into one box. The camera
then sits back along +X at a multiple of the model's height, so the framing
holds for whatever body sizes races introduce rather than being tuned to the
human male:

| Convar | Default | |
|---|---|---|
| `fo_charpreview_yaw` | `0` | model's facing |
| `fo_charpreview_dist` | `1.5` | distance back, × model height |
| `fo_charpreview_rise` | `-0.05` | camera offset from centre, × height; negative looks up |

`FramePreview` runs every layout pass rather than once on model change, so these
take effect live — framing is a judgement call about how the panel looks, and
the alternative is another edit-restart-screenshot round for each attempt.
`fo_ui_report` prints the measured height alongside all three.

None of these are saved convars. A saved convar beats a later change of default
(see *Options*), which is exactly how an earlier default change appeared to do
nothing.

### Hiding the main menu behind it

Helix only *dims* the main panel, so its button column and the schema title
stayed visible behind the load screen — the column is slightly wider than the
character list, so it showed as a sliver down the left edge.

Phoenix's load screen replaces the main menu view entirely; hiding it is the
equivalent. `OnSlideUp` / `OnSlideDown` are Helix's own transition hooks, so the
animation is unchanged.


### Sizes

Phoenix's is two compact panels rather than a full-screen split:

```lua
self.characters:SetPos(ScrW() * 0.1, ScrH() - (ScrH() * 0.2 + sH() * 0.45) - 24)
self.characters:SetSize(256, sH() * 0.45 + 24)
self.info:MoveRightOf(self.characters, 24)
self.info:SetSize(SW * 0.4, playerPanelTall)
```

Written scaled here, since their `sH()` with no argument returns 1080 and their
literal 256 would shrink at 1440p. Both panels are undocked first — Helix docks
them LEFT and FILL, and docking overwrites any manual position.

At 2560x1440: list 341x680, info 1024x680, together 1397 of 2560 wide and 680 of
1440 tall — where it previously covered nearly the whole window.


### The model: a model panel, not the carousel

Helix's `ixCharMenuCarousel` renders through a stencil-clipped `cam.Start3D`
with a transition between two ClientsideModels. It drew nothing here, and it is
far more machinery than this screen needs.

Phoenix uses a plain model panel (`nutCharacterPanel`, a DAdjustableModelPanel).
Helix ships the equivalent — `ixModelPanel`, already used in character creation —
so the carousel is hidden and one of those takes its place, pointed at the
selection from `OnCharacterButtonSelected`.

**Its `Paint` must not be overridden.** `DModelPanel:Paint` *is* the renderer —
it runs `LayoutEntity`, opens `cam.Start3D`, sets lighting and draws. Replacing
it with a background fill renders no model, which is the same failure the
carousel had. The backdrop goes on the parent panel instead.

`fo_ui_report` covers this panel — list width, header, selected character, and
whether the model panel's **entity** exists. That last one matters: a panel with
no entity renders nothing and looks identical to a broken Paint.


## Character creation

`fallout_ui/cl_creation.lua`. Diagnostics: `fo_create_report`.

Helix's flow is three subpanels that slide horizontally - faction, description,
attributes - each full-width with a model docked to one side. Phoenix's is a row
of compact frames appearing left to right as you commit to each step:

```lua
self.factions:SetPos(ScrW() * 0.1, ScrH() - (ScrH() * 0.2 + sH() * 0.45) - 24)
self.factions:SetSize(256, (sH() * 0.45) + 24)
self.info:SetPos(fX + self.factions:GetWide() + 12, fY)
self.info:SetSize(536, (sH() * 0.45) + 24)
```

### The flow is restyled, not replaced

The non-visual half is worth keeping: payload hooks, `VerifyProgression` running
each character var's `OnValidate`, the whitelist filter on the faction list, and
`SendPayload`. Phoenix's equivalents live in `sv_*.lua` files the scrapes never
captured, so replacing the flow means rewriting all of that blind.

So the subpanels, slide animation and progress bar stay. What changes is the
arrangement inside them - Helix's own panels are re-docked into columns, never
rebuilt, so `self.factionModel` and the payload hooks writing into them keep
pointing at live panels.

### The band

| Convar | Default | |
|---|---|---|
| `fo_create_height` | `0.45` | column height, fraction of screen |
| `fo_create_bottom` | `0.2` | gap below the columns, from the bottom up |
| `fo_create_width` | `1.0` | column width, as a multiple of Phoenix's |

The width is built from Phoenix's own columns - a 256px list, a 12px gap and a
536px info board, scaled - rather than a fraction of the screen. A fraction that
looks right at 1080p is half again too wide at 1440p, which the first attempt
did exactly: `0.62` of a 2560px screen is 1587px against Phoenix's ~1072.

Phoenix pins the group to `ScrW() * 0.1`; this centres it instead, because the
number of columns changes between steps (and again when races land) and a left
pin makes the group appear to drift sideways as you advance.

### One whitelisted faction skips the step entirely

`factionPanel.OnSetActive` jumps straight to `description` when
`#self.factionButtons == 1`, so with only `Wastelander` whitelisted the faction
column and info board are never shown. That is stock Helix behaviour, not a
layout fault - `ix.faction.HasWhitelist` passes only `isDefault` factions and
ones explicitly whitelisted for the player, and `NCR Trooper` is neither.
`fo_create_report` prints `factions listed` for this reason.

### The subpanel is not at (0, 0)

The band is produced with **dock padding on the subpanel**, not by resizing it:
`ixSubpanel` is the unit the slide animation moves, so it has to stay full-size.
Its children are inset instead.

That inset is in the subpanel's space, and `ixSubpanel:Init` sizes itself to
`parent - padding * 2` then calls `Center()` - so its origin is `(padding,
padding)`. The origin is derived from the subpanel's own **size**, not from
`GetPadding()` (they only agree while nothing has changed the padding since the
subpanels were built) and not from `GetPos()` (the slide animation moves them
horizontally, so mid-transition that bakes the animation offset into the padding
and the columns drift).

### The faction info board

New. Stock Helix shows `FACTION.description` nowhere in creation, so the only
thing telling two factions apart is the name and the model.

Phoenix gives the middle column artwork, blurb and the commit button.
`FACTION.image` is honoured if a faction sets one; none currently do, so the
slot falls back to the faction **model** - which is the thing you want to see
anyway, and is why the model panel is reparented into the board rather than kept
as a third column.

Refreshed from `Populate` (which runs on every return to the faction step, so it
always sees the current selection) and from a wrapper on each button's
`OnSelected` (because changing selection does not repopulate).

### SPECIAL rows

`ixAttributeBar` is Helix's widget, and SPECIAL rides on Helix attributes
(`libs/sh_special.lua` prunes the list to the seven), so this is the panel that
spends SPECIAL at creation. Init is wrapped, never replaced - it builds the
+/- buttons, their press-and-hold repeat through `Think`, and the value
animation. Only the drawing is swapped.

Values are drawn as discrete **notches**, which read as "5 of 10" where a smooth
bar does not - but only while each notch is wide enough to see. The ceiling is
`maxAttributes` (25), so above roughly fifteen it falls back to a plain fill.

Two traps found here, both invisible to a static check:

- **The list contains a non-SPECIAL bar.** Helix adds a points-remaining bar
  with `SetText(L("attribPointsLeft"))` and a green `SetColor`. It would have
  been given a meaningless "P" letter cell next to Perception's, so the cell is
  drawn only for names in `ix.special.isSpecial`, and `panel.color` drives the
  fill so the budget bar stays green.
- **The bars are nested one level deeper than they look.** The attributes
  character var wraps them in a plain `DPanel` before adding that to the
  container, so a direct-children search finds zero - which is also what a
  genuinely broken step reports. `fo_create_report` counts recursively.

Helix's `icon16/add.png` / `delete.png` are replaced with drawn glyphs: XP-era
16px icons that neither match this UI nor scale. **Do not clear the old icon
with `SetImage("")`** - that reaches `Material("")`, which returns nil, and
DImage indexes it unconditionally:

```
dimage.lua:120: attempt to index local 'Mat' (a nil value)
  4. Init - cl_creation.lua:101
  7. OnDisplay - helix/gamemode/core/libs/sh_character.lua:619
  9. Populate - cl_panels.lua:59
```

Note where that lands: inside `Populate`. One nil material in an attribute row
aborts the whole populate, so the symptom is not a missing icon - it is the
entire creation panel coming up blank behind a dimmed menu. Overriding `Paint`
already stops the image being drawn, so nothing needs clearing.

### The fields were solid yellow blocks

Two separate faults with one appearance.

`ixTextEntry:Paint` filled the WHOLE box with `color_primary` and drew black
only as a one-pixel shadow behind it. A field is a dark well with an accent
EDGE - the fill is the background, never the accent.

They were also enormous, and that is not a padding problem: Helix sets these to
`ixMenuButtonHugeFont`, and `ixTextEntry:SetFont` does `SetTall(text height)`,
so the box grows to fit whatever face it is given. The font is remapped in a
`SetFont` wrap rather than fixed after the fact, because `Populate` rebuilds
these panels and would undo anything applied later.

### The empty box on the left was the model

All three creation model panels are handed the faction's model, which is
`animations.mdl` - no visible mesh, so they render nothing and the description
step looks like it has a large empty column. Same cause as the character select
preview, same fix.

`SetPreviewModel` was refactored to take a MODEL PATH rather than a character
(creation has no character yet) and exposed as `ix.fallout.SetPreviewModel`, so
one composer serves both. Creation intercepts each panel's `SetModel` - which is
where Helix's `model` payload hook drives them - with an `ixComposing` re-entry
guard, since the composer sets the panel's model itself and would otherwise land
straight back in the override.

### Real customization needs races

Head, hair, beard, skin and face-skin choice is Phoenix's `nutCharCustomize`,
and it reads all of them out of race data: `genderHeads[skinColor]`,
`genderFaceSkins[...]`, `RACE.hairs`, `RACE.beards`. There is nothing to pick
from until `ix.races` exists.

The data survived the scrape - `libs/races/sh_race_human.lua` is 700 lines with
`genders`, `races` (ethnicities), `defaultModels`, `skins`, `heads`, `hairs`,
`beards` and `faceSkins` all present - so the customizer is buildable as soon as
races are ported.

### SPECIAL rows are one renderer, used twice

`ix.fallout.DrawSpecialRow` in `cl_widgets.lua`. Both the creation allocation
list and the F1 tab draw through it, rather than each having its own version -
two implementations that merely resemble each other drift, and nobody notices
until both are wrong in different ways.

Phoenix's row is a filled box with a DOUBLE border, two accent outlines a pixel
apart over a black one offset down-right:

```lua
surface.DrawRect(0, 0, w, h)                  -- color_background
surface.DrawOutlinedRect(2, 2, w - 1, h - 1)  -- black
surface.DrawOutlinedRect(0, 0, w, h)          -- color_primary
surface.DrawOutlinedRect(1, 1, w - 2, h - 2)  -- color_primary
```

then the initial, name and value as three fixed columns with the action
right-aligned. An earlier version drew the value as notches instead; that reads
well for a small maximum but the ceiling here is `maxAttributes` (25), and it is
not what Phoenix does.

### DImageButton holds a child DImage

Overriding a `DImageButton`'s `Paint` does **not** remove its icon. The class is
a `DButton` that creates `self.m_Image = vgui.Create("DImage", self)`, and that
child paints itself on top of whatever the button draws - which is why Helix's
icon16 add/delete circles survived being painted over.

`SetImageVisible(false)` is the switch. Not `SetImage("")`, which reaches
`Material("")` and crashes DImage.

The +/- buttons are also both docked RIGHT, with explicit `SetZPos`: docking
processes children in ascending z and the first one processed lands OUTERMOST,
so without it `sub` (created first) ends up right of `add` and the pair reads
"+ -".

### Per-panel model zoom

`ix.fallout.SetPreviewModel`'s framing takes a per-panel `ixZoom`, because
creation frames tighter than character select - its column is narrower and
taller, so the distance tuned for the select screen leaves the body small and
marooned in it.

`ixZoom` may be a number or a FUNCTION. Creation passes a function returning
`fo_create_modelzoom` (default `2.0`), so the convar re-frames live; a captured
number would need a menu reopen to take effect.

### Panel class, not panel name

**That advice was wrong, and is corrected in `07-gotchas.md`.**
`GetClassName()` returns the ENGINE class, never the `vgui.Register` name.
Match on the `ClassName` Lua field instead.

## Verifying a change

You cannot boot the server from tool context, so:

```bash
python _docs/tools/luacheck.py garrysmod/gamemodes/falloutrp
```

`luacheck.py` is now a **real tokenizer** — long brackets, all comment forms,

### Brackets escape a scroll panel's clip

`ix.fallout.DrawBrackets` calls `DisableClipping(true)` so the rules can be
drawn a couple of pixels OUTSIDE the panel — that overdraw is the motif, and on
a container it is exactly right.

Inside a **scroll list** it is not. `DisableClipping` does not merely let that
panel draw past its own edge; it lifts the scissor for the whole draw, so rows
near the bottom of the list render straight through the viewport and out over
whatever is beneath the panel.

`SetNoOverdraw(true)` on `ixFOPanelBracketed` (and the `bNoOverdraw` argument to
`DrawBrackets`) keeps the rules inside the bounds and skips `DisableClipping`
entirely. At scale 1 on a 42px row:

| | top rule | side ticks | bottom rule ends |
|---|---|---|---|
| overdraw | `y = -2` | `x = -2`, `x = w` | `y = 44` (outside) |
| no overdraw | `y = 0` | `x = 0`, `x = w-2` | `y = 42` (inside) |

Only the developer terminal's rows need it today. Every other bracketed panel is
a **container** — the carousel, the creation columns, the menu window and side
panels — where overdrawing its own edge is the intended look.
